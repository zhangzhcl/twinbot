# TwinBot Server Deployment Guide (bootstrap)

The desktop installer is only a client. To make the system work, deploy two services on **your own Ubuntu/Debian server(s)**:

- **Control plane** (required): database + task scheduling + model config storage — this is what the desktop client connects to;
- **Execution pod** (one container per user): cloud code runs here; artifact pages are proxied back through the control plane.

About 15 minutes total; the servers only need Docker.

## Execution order (servers first, desktop last)

All deployment happens **on your own cloud servers** (inside an SSH terminal); the desktop app does not participate in deployment — it is the client that connects at the end:

1. **SSH into the control server** → unzip the deploy bundle → run `deploy/bootstrap/deploy-control.sh` (interactive: domain + user count) — generates the desktop three-line config and `runtime.env`;
2. **Copy `runtime.env` to the execution server** (scp/USB) → SSH into the execution server → unzip the bundle → run `deploy/bootstrap/deploy-runtime.sh` — the pod starts and connects back to the control plane;
3. **Start the desktop app last** (Windows PC) → the "Connection" settings tab opens automatically on first launch → paste the three-line config → restart → connected.

The order cannot be reordered: the three lines the desktop needs are generated by the control script, and the WSS address the pod connects to lives in the same output.

## 0. Prerequisites

- One 2C4G+ Ubuntu/Debian server (control plane) with Docker installed;
- A domain resolved to that server (the desktop client requires a wss encrypted connection; the bundled Caddy issues certificates automatically);
- For a separate execution server: one more 4C8G server.

## 1. Control plane (one command)

```bash
unzip twinbot-server-deploy.zip && cd twinbot-server-deploy
bash deploy/bootstrap/deploy-control.sh
```

The script asks for the **public domain**, **user count** and **port**, then automatically:

- Generates the database password, admin token, per-user access tokens and per-pod runtime tokens (all random, written to `deploy/control/.env`);
- Builds and starts the control plane (PostgreSQL + Control API + a Caddy automatic-HTTPS gateway);
- Generates `runtime.env` (for the execution server) and `twinbot-desktop-config.txt` (the three-line connection config for the desktop client).

A passing health check means the deployment succeeded.

## 2. Execution pod (one container per user)

```bash
# Copy the generated runtime.env to the execution server's bundle root, then:
bash deploy/bootstrap/deploy-runtime.sh
```

Builds and starts the pod containers (bundled with Chromium / Python3 / Node), which connect back to the control plane automatically. The bundled image supports 2 users out of the box; for more users duplicate a service block in `deploy/runtime/docker-compose.yaml` (one data volume per user).

## 3. Desktop client (per user)

Send the user the three lines from `twinbot-desktop-config.txt`:

- `CONTROL_API_URL` / `CONTROL_WS_URL` / the user's access token;

On first launch the desktop app automatically opens the "Connection" settings tab — paste the values and restart. Model keys are configured per user in the "Model" settings tab (isolated between users).

## 4. Operations

```bash
docker compose logs control-api      # control plane logs
docker compose logs runtime-user-a   # pod logs
docker compose down                  # stop (data volumes are kept)
```

- Sessions / model profiles / audit data live in the control-plane database — back up the `postgres-data` volume;
- Per-user pod data lives in the `workspace-user-*` volumes;
- Adding a user = add tokens in the control `.env` + add a container on the execution server (see above).
